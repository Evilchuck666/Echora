# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Project

Echora is the backend API for a self-hosted music streaming service: it catalogs a folder of FLAC/MP3 files and serves them over HTTP for clients to download and play.

- Stack: PHP 8.5, Symfony 8.1, API Platform 5, PostgreSQL 16 via Doctrine ORM, served by FrankenPHP. Docker setup based on the `dunglas/symfony-docker` template.
- This repo is the API only. The web client (React + TypeScript) lives in a separate repo at `../echora-web` (in production it is built into this image and served by the same Caddy, see below), and native apps for other platforms are planned. When an API change affects clients (fields, endpoints, auth), say so: `../echora-web/CLAUDE.md` documents how the client uses the API.
- Why the API is the way it is: `docs/decisions/` keeps one record per decision that shaped it (context, decision, consequences, origin, commits). Many were taken from the echora-web repository's sessions. A new decision about the API gets a new record there (next free number, added to its index), whichever repository it is taken from, with only the reasons actually given; a record that no longer holds is marked superseded, not deleted.
- The "ask before generating" questions in AGENTS.md are answered: Doctrine ORM, a JSON API built with API Platform (no Twig), and multi-user JWT authentication (LexikJWT + gesdinet refresh tokens).

## Architecture rules

- The API is the only contract between server and clients. Return JSON, not server-rendered pages, and don't add behavior that only works for the web frontend: future native apps must be able to do everything through the same endpoints.
- Audio endpoints must support HTTP Range requests (`206 Partial Content`, `Accept-Ranges: bytes`). Library files (audio, covers) are served by plain Symfony controllers (`TrackStreamController`, `TrackOpusStreamController`, `AlbumCoverController`, `ArtistCoverController`) through `LibraryFiles`; they're documented in OpenAPI by `LibraryFilesOpenApiFactory`.
- Production serves the web client too: `compose.prod.yaml` passes the echora-web checkout (`WEB_DIR`, default `../echora-web`) as the `web` build context, the Dockerfile's `web_build` stage runs `bun install --frozen-lockfile` and `bun run build`, and `frankenphp_prod` copies `dist/` to `/srv/web`. The Caddyfile's `@webClient` serves it (SPA fallback to `index.html`, immutable `/assets`) for every path except `/api`, `/bundles`, `/.well-known`, the profiler and `index.php`, only when `/srv/web/index.html` exists: development images don't have it, so dev routing is unchanged. Same origin, so production CORS defaults to no origin (`^$`). Keep new API-side public paths out of `@webClient`.
- Every folder PHP writes to at runtime in production must exist in the image owned by `www-data` (`install -d -o www-data -g 0`): a volume mounted on a path missing from the image is created root-owned (it broke `var/media`).
- Files are sent by Caddy, never streamed by PHP: behind FrankenPHP, `BinaryFileResponse` answers with `X-Accel-Redirect` and the Caddyfile's `intercept` serves the file with `file_server` (ranges included). PHP streaming broke playback: players read a track slowly, `max_execution_time` (30 s) killed the response, and Xdebug wrote its error page into the audio, which Firefox then played as silence. The Caddyfile overwrites the `X-Sendfile-Type` and `X-Accel-Mapping` request headers (a client-sent mapping could expose any file) and only serves paths under `/music/` and `/app/var/media/`: keep both. Without those headers (tests), PHP streams the file. The Caddyfile is bind-mounted in development (`docker compose restart php` after a change) and copied into the production image (rebuild).
- The music folder is mounted read-only at `/music` (`MUSIC_LIBRARY_PATH`; `MUSIC_DIR` on the host). Never write to it. `app:library:scan` (`LibraryScanner`) is the only way tracks get into the database.
- Never expose a track's `path` or `fileModifiedAt`, an album's `coverPath`, `downloadedCover` or `coverLookedUpAt`, or an artist's `imagePath`, `downloadedImage` or `imageLookedUpAt`: they describe the server's disk. Serialization uses explicit `*:read` groups; `track:item` (lyrics) is only for `GET /api/tracks/{id}`, to keep lists light.
- Artist images (`ArtistImages`, the last step of a scan): `artist`/`folder` in the artist folder (the common parent of the artist's album folders, never the library root), or else downloaded from TheAudioDB (`TheAudioDb`: free key `123` in `THEAUDIODB_API_KEY`, empty in `.env.test`; 30 requests a minute, a 429 stops the lookups for that scan; only an exact name match, ignoring case and accents). Downloads and thumbnails live in `%app.media_dir%` (`var/media/<env>`, the `media` volume in prod), never in the music folder. `/api/artists/{id}/cover` always serves a `Thumbnails` JPEG (GD, in the Docker image), not the original. Tests never reach the network: they replace `TheAudioDb` with a `MockHttpClient`.
- Album covers (`AlbumCovers`, a scan step before `ArtistImages`): from the album folder (`CoverFinder`), found again on every scan, or else downloaded from TheAudioDB (`TheAudioDb::findAlbumCover()`, `searchalbum.php`; exact album artist and title match) into `%app.media_dir%/albums`, served as is (no thumbnail). Tracks show their album's `coverUrl`. Both steps share the rate limit and `ScanReport::$theAudioDbFailure`: a 429 on an album stops the artist lookups too.
- Opus (`OpusTranscoder`, `GET /api/tracks/{id}/stream/opus`, the track's `opusStreamUrl`): FLAC only (an MP3 would lose quality twice), 256 kbit/s Ogg Opus made by `opusenc` (`opus-tools`; the prod stage copies the binary and its libraries like `file`) on the first request, under a `symfony/lock` lock per track, into `%app.media_dir%/transcodes`, then served like any library file (X-Accel-Redirect). Never stream an encoder's output through PHP: no Range, and the problems described above. A file's access time is its last use (`app:transcodes:prune` reads it); never change its modification time, as Caddy's ETag (which players send back in `If-Range`) comes from it.
- Converting ahead of time (`POST /api/transcodes`, `TranscodeRequestController`, documented by `TranscodesOpenApiFactory`; docs/decisions/0011): clients send their `device` (a UUID they generate once, required) and the next tracks of its queue (at most 20, ids or IRIs). `TranscodeQueue` answers at once (202, `queued`/`ready`/`converting`) and sends one `TranscodeTracks` message per request to the Messenger transport `transcodes` (Doctrine, `messenger_messages` in PostgreSQL, woken by `pg_notify`; `in-memory://` in tests). `TranscodeTracksHandler` converts one track per message with `OpusTranscoder::transcodeUnlessBusy()` (never waits for the per-track lock) and sends the rest of the list back to the queue (`TranscodeQueue::requeue()`), so lists take turns (docs/decisions/0012) in the `messenger:consume transcodes` workers that `docker-entrypoint` starts next to FrankenPHP (`TRANSCODE_WORKERS`, default 1, one `opusenc` each): never convert ahead of time in a worker that serves HTTP. Each request replaces the previous one of the same device; an account keeps the lists of its `MAX_DEVICES` (5) most recent devices (one `cache.app` item per user, device → latest request id, updated under a lock and read by `TranscodeQueue::isLatest()` before each track), so old lists never pile up: keep at most one message per list in the queue, never one per track. `OpusTranscoder::check()` marks a ready file as used, so `app:transcodes:prune` keeps what is about to be played. Failures are logged, never retried. After changing the handler, the queue, the transcoder or the message, `docker compose restart php`: `messenger:stop-workers` only reaches an idle worker when the next message wakes it, and that message is handled (or, if the message class changed, crashes the worker) with the old code. A message whose worker crashed stays `delivered` until the transport's `redeliver_timeout` (1 hour), then is handled again (and dropped if its list is no longer the latest).
- Scheduled jobs live in `frankenphp/crontab`, run by Supercronic (pinned with a checksum in the `Dockerfile`), which `docker-entrypoint` starts in the background next to FrankenPHP, in dev and prod: no host cron, no extra container. Add jobs there, not to the host.
- A track is its file's audio, not its path: `TagReader::audioHash()` (`flac:` + the STREAMINFO MD5 that getID3 reads with the header, `mp3:` + XXH128 of the frames between `avdataoffset` and `avdataend`, without ID3/APE), stored in `Track::$audioHash` (not exposed). `LibraryScanner` lists the folder first, then a new file whose hash matches exactly one missing track (or, if several, exactly one with the same title) takes over that track with `Track::moveTo()`: same id, new path and tags, `ScanReport::$moved`. Anything that references tracks (favorites, playlists) must use the track id, never the path. The test fixtures all have the same FLAC audio (silence).
- Favourites (`Favourite`, docs/decisions/0009): per user, of exactly one track, album or artist (a `CHECK` in the migration; Doctrine doesn't map it), deleted with the user or the item (`ON DELETE CASCADE`). `FavouriteController` (`PUT`/`DELETE /api/{tracks,albums,artists}/{id}/favourite`, documented by `FavouritesOpenApiFactory`) writes with SQL (`INSERT ... ON CONFLICT DO NOTHING`), so it's idempotent even with two requests at once. The lists are `GetCollection` operations named `favourites_<kind>s` (`/api/favourites/...`), filtered and ordered (newest first) by `FavouritesExtension`; `TrackOrderExtension` steps aside for them. The `favourite` field of tracks, albums and artists is filled by `FavouriteNormalizer` from `CurrentFavourites`, which reads the user's ids of a kind once per request and is reset between requests (`ResetInterface`: workers serve many users). Keep it that way: one query per kind, never one per item. Responses depend on the user: never cache them in a shared cache.
- Playlists (`Playlist`, `PlaylistItem`, docs/decisions/0009): per user, deleted with the user; items deleted with their playlist and their track (`ON DELETE CASCADE`). API Platform resources; `OwnedByCurrentUserExtension` hides other users' playlists and items (404, never 403), and `PlaylistItemsProvider` checks the owner itself for `GET /api/playlists/{id}/items`. Every change to items goes through `PlaylistEditor`, in a transaction that first locks the playlist row (`SELECT ... FOR UPDATE`): keep it that way (`PlaylistConcurrencyTest` runs real processes, with `#[SkipDatabaseRollback]`). Manual orders (the items of a playlist, by `playlist_id`, and the playlists of a user, by `owner_id`) both use `App\Ordering\SortKeys`: `sort_key` (BIGINT, unique in its scope, positive by a `CHECK`, never exposed) with gaps of `SortKeys::STEP`: append = last + step, prepend = half the first, move = middle of the new neighbours (or renumber above the highest key when they touch), remove = nothing else changes. Reuse it for any new manual order. The exposed `position` is computed (index from 0: offset + rank in the page, or a `COUNT` for one row), so deleting rows (a scan deleting tracks) needs no renumbering; `LibraryScanner` only touches `updated_at` of their playlists first (`PlaylistRepository::touchPlaylistsOfTracksAt()`). `trackCount`, `durationMs` and `covers` are filled by `PlaylistSummaries` for a whole page in two queries (`PlaylistProvider`, `PlaylistProcessor`, `AddPlaylistTracksProcessor`): never one query per playlist (tested by counting queries with `doctrine.debug_data_holder`). Playlists of a user (`PlaylistOrder`): new ones first, moved by `PATCH /api/playlists/{id}` with `position` (`Playlist::setPosition()` records it, `PlaylistProcessor` applies it after the new name), under a lock on the user's row (`SELECT ... FOR NO KEY UPDATE`, not `FOR UPDATE`, so rows referencing the user can still be inserted). Moving doesn't change `updatedAt`; `Playlist::setName()` does, only for a different name. PATCH bodies are `application/merge-patch+json`. Positions are indexes in the order when the request arrives: clients send moves one at a time.
- Library scans (docs/decisions/0015) go through `LibraryScans`, which records each one as a `LibraryScan` (status `queued`/`running`/`finished`/`failed`, trigger `api`/`console`/`schedule`, the report; `failures` lists unreadable files by their path inside the library, administrators only). `POST /api/library/scan` (administrators) queues a `ScanLibrary` message on the Messenger transport `library` (its own worker in `docker-entrypoint`, `redeliver_timeout` 24 h; `in-memory://` in tests), `app:library:scan` runs at once, and `frankenphp/crontab` runs it every night with `--scheduled`. One scan at a time: a new one is refused (409, or a warning for `--scheduled`) while another is queued or running; a scan runs under the `library-scan` lock, and one still `running` while that lock is free was interrupted and is failed by the next request. While it runs, `LibraryScanner::scan()` (and `AlbumCovers`/`ArtistImages::update()`) call a `$progress(ScanPhase, done, total)` callback; `LibraryScanProgress` writes it to the scan's `phase`/`phase_done`/`phase_total` with SQL, at most once a second (plus at every new phase and its end), and `finish()`/`fail()` clear it. The scanner clears the entity manager every 100 files: never touch the `LibraryScan` entity during the scan, and reload it after (`LibraryScans::run()`). Call `LibraryScanner` directly only in tests. After changing code the library worker runs (`ScanLibraryHandler`, `LibraryScans`, `LibraryScanner` and its steps), `docker compose restart php`, as for the Opus workers: the worker keeps the classes it loaded, and `docker compose up --build` doesn't recreate an unchanged container (a scan once ran without its progress for that reason).
- When the scanner learns to read a new tag, existing tracks only get it with `app:library:scan --full`: say so in the README and the change summary.
- `GET /api/search` (`App\ApiResource\Search`, a DTO resource with `SearchProvider`) runs `LibrarySearch`: every word must match (`LIKE`, escaped), case- and accent-insensitive through the `UNACCENT()` DQL function (`App\Doctrine\Unaccent`, PostgreSQL's `unaccent` extension, enabled by a migration). It fetches the related artists and albums in the same query; keep it that way (one count and one select per kind).
- API Platform 5 deprecates `#[ApiFilter]`, `SearchFilter` and `OrderFilter`: filter with `#[QueryParameter]` and the per-strategy filters (`PartialSearchFilter`, `ExactFilter`, `IriFilter`, `SortFilter`). API tests extend `ApiPlatform\Test\ApiTestCase`, not the deprecated `ApiPlatform\Symfony\Bundle\Test\ApiTestCase`.

## Security

- Everything under `/api` requires `ROLE_USER` except the docs, `/api/auth`, `/api/token/refresh`, `/api/logout`, `/api/setup`, the stream and cover routes (tracks, albums, artists) and `GET /api/users/{id}/avatar` (see `access_control` in `security.yaml`). New public routes must be added there deliberately.
- The stream and cover routes accept a JWT or the `UriSigner` signature of the track's `streamUrl` / `opusStreamUrl` / album's `coverUrl` (`SignedUrlGenerator`, filled by `SignedUrlNormalizer`; checked by `LibraryFiles::denyUnlessAuthorized()`), because players and `<img>` can't send headers. Never put a JWT in a URL. `UriSigner::sign()` reads an `int` as an absolute timestamp: pass a `DateInterval` for a lifetime. Cover URLs expire at a fixed time (end of tomorrow, UTC) so they stay identical all day and browsers can cache them.
- Accounts (docs/decisions/0013), like Immich: no sign-up. While there is no account, `POST /api/setup` (public, `App\ApiResource\Setup`) creates the administrator and returns a token pair (`SessionTokens`, Lexik's success handler, so gesdinet adds the refresh token); then 409. Administrators manage accounts through `/api/users` (`security: is_granted('ROLE_ADMIN')`), everyone their own through `/api/me` (`PATCH` with group `user:self`: `name`, `username`, `email`; `POST /api/me/password`). Every creation, change of role and deletion goes through `UserAccounts`, under one `symfony/lock` lock (`user-accounts`): one administrator at setup, never zero afterwards (counted in SQL, not from loaded entities), an administrator never deletes themselves. New accounts give an email and a name; the username is made from the email (`ana`, `ana-2`). Sign-in takes the username or the email (`UserRepository::loadUserByIdentifier()`, the entity provider's loader).
- Sessions name accounts by id: `User::getUserIdentifier()` returns the id, the JWT carries it in `sub` (`user_id_claim`; `User` has no `sub` property, so Lexik falls back to `getUserIdentifier()`, while a `username` claim would read `getUsername()`), and refresh tokens store it (a migration rewrote the old ones). Renaming an account keeps its sessions; signing out deletes its refresh tokens by id (`UserAccounts::signOut()`). Never identify sessions by username or email again.
- Profile pictures (`UserAvatarController`, documented by `UserAvatarsOpenApiFactory`): `POST` multipart (`file`, ≤ 5 MB, type read by `getimagesize()`, never the client's), made into a JPEG square by `Thumbnails::of()` (`avatar-{id}`), its file name in `User::$avatar` (never exposed), served by Caddy to a JWT or the signed `avatarUrl` (`SignedUrlGenerator::avatar()`, file name in the URL so a new picture gets a new URL). `POST`, not `PUT`: PHP only parses multipart bodies for POST.
- The `app:user:*` commands remain for recovery (`create <email>`, `password` and `delete` take a username or email). Passwords are asked with a hidden prompt (`PasswordPrompt`), never taken as arguments. Symfony 8 doesn't turn interactivity off without a TTY, so `PasswordPrompt` checks `stream_isatty()` itself.
- Sign-in throttling (docs/decisions/0014): `POST /api/auth` has a firewall of its own (`login`), with `login_throttling` (5 per account and address, 25 per address, 15 minutes; a success clears the account's count, not the address's). Keep `json_login` out of the `api` firewall: there, every expired JWT or spent refresh token is a `LoginFailureEvent` too, and would lock clients out after waking up (`SignInThrottlingTest` checks it). `LoginFailureHandler` turns throttled attempts into 429 with `Retry-After` (Lexik's handler answers the rest). `POST /api/me/password` counts wrong current passwords in the `password_change` rate limiter, per account. Limits are kept in `cache.rate_limiter` (`cache.app`; PostgreSQL in tests, so DAMA rolls them back and requests share them). Addresses come from `TRUSTED_PROXIES` when Echora is behind another proxy (empty: X-Forwarded-For is ignored).
- Refresh tokens are single use, stored hashed, with reuse detection (`gesdinet_jwt_refresh_token.yaml`). Signing an account out means deleting its rows from `refresh_tokens`.
- The bundle looks a refresh token up in its authenticator and deletes it later in the same request, so concurrent refreshes with the same token would both succeed. `RefreshTokenLockListener` holds a `symfony/lock` lock on the token (PostgreSQL advisory locks: `LOCK_DSN` in `compose.yaml`) from before the firewall until the request finishes, so the second request is treated as reuse.
- The refresh firewall's `check_path` is the path `/api/token/refresh`, not the route name: the bundle documents it in OpenAPI as written, and a route name ended up as a bogus path.
- Grace period for lost refresh responses (`RefreshTokenGraceListener`, `RefreshTokenSuccessors`, `RefreshTokenSuccessorExtractor`): after a refresh, the presented token is mapped to the issued one for `REFRESH_TOKEN_GRACE_SECONDS` (300), encrypted with a key derived from the presented token and `kernel.secret`. A spent token presented again while its successor is unused is refreshed as that successor (an extractor at the head of the bundle's chain, so the authenticator, the rotation and the lock all see it); the mapping always starts from the token the client presented, never from the successor, so a used successor or a chain walk never revives a token. Concurrent duplicates are still reuse (the grace listener runs before the lock). Spent tokens and successors are in the persistent `cache.refresh_tokens` pool (PostgreSQL `cache_items`): never move them back to `cache.app`, which is wiped on deploy. Expired rows stay until `bin/console cache:pool:prune`.
- `POST /api/logout` is the firewall's `logout`; the bundle's listener (`invalidate_token_on_logout`) deletes the refresh token in the body. It is documented by `LogoutOpenApiFactory`.
- The JWT key pair is generated by the entrypoint on the first start (`config/jwt`, git- and docker-ignored; the `jwt_keys` volume in prod) with `chmod 600` on the private key.

## Testing

- CI has two jobs: `tests` (dev image: style, PHPStan, PHPUnit, schema) and `production` (the prod image, built with echora-web's `main` checked out next to this repository, started with `tests/Fixtures/music`, then `scripts/smoke-test-prod.sh`). When a change affects how production serves something (Caddyfile, Dockerfile prod stages, `compose.prod.yaml`, media, auth), add a check to the smoke test. It must keep working against any deployed library: no fixture names. Accounts are created through a pseudo-terminal: `printf 'pw\npw\n' | script -qec "docker compose exec php bin/console app:user:create <email>" /dev/null`.
- `bruno/` is a Bruno collection of every endpoint (`.bru` files, credentials in the git-ignored `bruno/.env`). Update it in the same change whenever an endpoint, a parameter or the authentication changes.

- Tests scan `tests/Fixtures/music` (set in `.env.test`), never the real library. The fixtures are one-second silent files generated with ffmpeg (covers: 8×8 images); add new cases the same way and keep them tiny. ffmpeg writes MP3 lyrics as a TXXX frame, not USLT: use mutagen (`python3`) for a real USLT.
- The test client doesn't capture the body of a `BinaryFileResponse`; send it to an output buffer (see `TrackStreamTest::body()`).
- API tests authenticate with the `CreatesUsers` trait (`createUser()`, `tokenFor()`) and `$client->setDefaultOptions(['auth_bearer' => ...])`.
- `PlaylistConcurrencyTest` holds a lock from a second connection and releases it in a `finally`: if a test fails while holding it, `tearDown()`'s `TRUNCATE` waits for it forever. `PlaylistOrderMigrationTest` runs a migration down and up inside the DAMA transaction, rebooting the kernel in between (a migration runs once per process).
- API tests that check Messenger messages call `$client->disableReboot()` and collect `InMemoryTransport::getSent()` after each request: the services (the transport included) are reset before every request (see `TranscodeRequestTest`).
- To try a command that asks for a password from a non-interactive shell, give it a pseudo-terminal: `script -qec "docker compose exec php bin/console app:user:create <email>" /dev/null`.
- `SetupConcurrencyTest` holds the `user-accounts` lock and starts real processes (`tests/Accounts/post-setup.php` handles `POST /api/setup` with the kernel, using no private service); advisory locks live in the database of `LOCK_DSN`, so it counts waiting sessions in every database.

## Gotchas

- A PostToolUse hook (`.claude/hooks/php-cs-fixer.sh`) formats every PHP file you write or edit with PHP-CS-Fixer, when the stack is running. Expect files to change after an edit (e.g. unused imports removed); re-read before editing the same region again.
- A PostToolUse hook (`.claude/hooks/fix-permissions.sh`) runs `scripts/fix-permissions.sh` automatically after every Bash command containing `docker compose exec` or `docker compose run`, so don't run it by hand after those. Run it manually only if root-owned files appeared some other way.
- `composer.json` declares `GPL-3.0-only`. Don't let a skeleton or recipe overwrite `LICENSE` with an MIT text: check `git diff LICENSE` after any scaffolding.
- Flex skips `contrib` recipes (`allow-contrib: false`): `dama/doctrine-test-bundle`, `gesdinet/jwt-refresh-token-bundle` and PHPStan had to be configured by hand.
- Changes to `frankenphp/docker-entrypoint.sh` or `frankenphp/crontab` need `docker compose up --build --wait`: both are copied into the image, not bind-mounted.
- Quote regular expressions in YAML (`path: '^/api/tracks/[^/]+/stream$'`): inside `{ ... }` an unquoted `[` starts a list. Symfony's lenient parser accepts it, so `lint:yaml` and the tests pass, but strict parsers (the VS Code YAML extension) report the rest of the file as broken.
- The database service publishes port 5432 on a random host port (`docker compose port database 5432`), because the host already runs its own PostgreSQL on 5432.
